## 1. Executive Summary & Context

This document provides the definitive comparison, technical mapping, and functional differentiation between the **6 user roles** defined in the [Pitch It PRD](../PRD.md) and the existing infrastructure of **Kriyadocs 2.0** (`kriya2.0`, `kriya2.0_view`, `elasticnodeproxy`).

In Kriyadocs 2.0, user roles are stored in Elasticsearch as multi-tenant tuples:
```json
{
  "customer-name": "bmj",
  "role-type": "publisher" | "production" | "author",
  "access-level": "handlingeditor" | "associateeditor" | "author" | "reviewer" | "admin" | "manager"
}
```

### Architectural Golden Rule:
> **Zero schema changes or database migrations are required in Kriyadocs 2.0.**  
> Kriyadocs already possesses all core user types. The **Editor-in-Chief (EIC)** is configured per journal in Kriyadocs (`projectList.xml` $\rightarrow$ `<eic-email>`), and Pitch It resolves EIC privileges dynamically in code.

## 4. Key Architectural Nuances & Differences

### 4.1 Handling Editor vs. Editor-in-Chief (EIC)
* **The Core Difference:** Handling Editors screen papers, invite reviewers, and make preliminary triage decisions. In double-blind journals, they are **never** permitted to see the author's real face or voice.
* **Why EIC is Special:** Only the Editor-in-Chief holds **Master Unblinding Rights**. If an author is suspected of academic fraud, deepfake impersonation, or conflict of interest, the EIC can toggle the original un-anonymized video stream.
* **Why Kriya Doesn't Need an "EIC" Role:** In Kriyadocs, EICs are designated per journal via `<eic-email>` in `kriya2.0_view/db/kriyadocs/customers/{customer}/projectList.xml`:
  ```xml
  <project>
      <name>archdischild</name>
      <fullName>Archives of Disease in Childhood</fullName>
      <parameters>
          <eic-email>josef.smolen@meduniwien.ac.at</eic-email>
          <publisher-email>production.ard@bmj.com</publisher-email>
      </parameters>
  </project>
  ```
  This is cleaner than a global role because a professor might be the Editor-in-Chief of *Journal A*, but an ordinary author submitting to *Journal B*. Pitch It dynamically elevates them to EIC based on the manuscript's journal.

### 4.2 Existing Reviewer vs. New Guest Reviewer
* **Existing Reviewers:** Already reside in Kriyadocs' Elasticsearch database. Editors search them by keywords, past turnaround metrics, and affiliation via `getuserswithjournals`.
* **New Guest Reviewers:** Added on-the-fly by the editor using just an email and name. Kriyadocs does not create a full login account immediately; Pitch It issues a stateless 14-day HMAC magic token. The reviewer experiences zero password friction, with an optional account claim after submitting their review.

## 6. Technical Resolution Implementation in Code

This TypeScript resolution engine resides in `server/src/services/kriyadocs.service.ts` to map incoming Kriyadocs user sessions into Pitch It roles:

```ts
// server/src/services/kriyadocs.service.ts

export type PitchItRole = 
  | 'AUTHOR' 
  | 'HANDLING_EDITOR' 
  | 'EDITOR_IN_CHIEF' 
  | 'REVIEWER_EXISTING' 
  | 'REVIEWER_GUEST' 
  | 'PUBLISHER_ADMIN';

interface KriyaRoleTuple {
  customerName: string;
  roleType: string;
  accessLevel: string;
}

interface UserContext {
  email: string;
  roles: KriyaRoleTuple[];
}

interface JournalContext {
  journalCode: string;
  eicEmail?: string;
}

/**
 * Resolves a Kriyadocs user's effective Pitch It role for a specific manuscript/journal.
 */
export function resolveEffectiveRole(
  user: UserContext,
  journal: JournalContext
): PitchItRole {
  const normalizedUserEmail = user.email.toLowerCase().trim();
  const normalizedEicEmail = journal.eicEmail?.toLowerCase().trim();

  // 1. Check if user is the designated Editor-in-Chief for this journal
  if (normalizedEicEmail && normalizedUserEmail === normalizedEicEmail) {
    return 'EDITOR_IN_CHIEF';
  }

  // 2. Locate active role for this customer
  const activeRole = user.roles.find(
    (r) => r.customerName.toLowerCase() === journal.journalCode.toLowerCase()
  ) || user.roles[0];

  if (!activeRole) {
    return 'AUTHOR'; // Default fallback
  }

  const accessLevel = activeRole.accessLevel.toLowerCase().trim();

  // 3. Map Kriyadocs access-levels
  switch (accessLevel) {
    case 'admin':
    case 'manager':
      return 'PUBLISHER_ADMIN';

    case 'handlingeditor':
    case 'associateeditor':
      return 'HANDLING_EDITOR';

    case 'reviewer':
      return 'REVIEWER_EXISTING';

    case 'author':
    default:
      return 'AUTHOR';
  }
}
```

## 7. Summary Checklist for Engineering

- [x] **No Kriya Database Migrations:** Existing Kriyadocs roles (`author`, `handlingeditor`, `associateeditor`, `reviewer`, `admin`) are reused as-is.
- [x] **Handling vs. EIC Separation:** Handling Editors get anonymized streams only; EIC gets master unblinding rights governed by journal `<eic-email>`.
- [x] **Guest Reviewers Isolated:** Guest reviewers use stateless 14-day signed tokens stored in PostgreSQL with no initial Kriyadocs account overhead.
- [x] **Confidentiality Gate Enforced:** Manuscript PDF download is strictly locked for reviewers until they click *"Accept"*.
