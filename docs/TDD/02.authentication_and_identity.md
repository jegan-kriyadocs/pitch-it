## 1. Executive Summary & Architectural Scope

This document specifies the technical architecture for **Authentication**, **Researcher Identity Verification (KYC)**, and **Role-Based Access Control (RBAC)** across the **Pitch It** platform.

### Core Architectural Decisions:
1. **Per-Journal Membership Model:** Users do not have one flat global role. A user can be an Author on Journal A, an Associate Editor on Journal B, and an invited Reviewer on Journal C. Roles are scoped to journal memberships.
2. **Asymmetric In-Context Launch (Flow A — Primary):** Kriyadocs launches Pitch It in a **new tab (`target="_blank"`)** with an **RS256-signed launch token** containing a single-use `jti` to prevent replay attacks. Pitch It exchanges this token for an HTTP-only, `SameSite=Lax` session cookie.
3. **Opaque Hashed Magic Links (Zero JWT Leakage):** Reviewers arrive via high-entropy, 32-byte opaque tokens stored as SHA-256 hashes in PostgreSQL. No reviewer identities, email addresses, or manuscript titles are serialized into URLs or HTTP logs, preserving strict double-blind privacy.
4. **Journal-Level EIC Unblinding Rights:** Pitch It evaluates Editor-in-Chief privileges dynamically against the journal's configured `<eic-email>` (from Kriyadocs `projectList.xml`), eliminating the need for any schema changes in Kriyadocs.
5. **Direct ORCID Public API Ingest:** Pitch It queries ORCID's public REST API directly to verify academic footprint ($\ge 2$ trusted-source works from Crossref/DataCite) for KYC trust tier evaluation.

## 3. The 6 User Roles & Per-Journal Membership Architecture

> **Complete Mapping Table**: See companion document [`03.kriyadocs_role_mapping.md`](./03.kriyadocs_role_mapping.md) for the side-by-side comparative matrices.

### 3.1 Per-Journal Role Scoping
In academic publishing, user roles are contextual:
* Dr. Sarah Jenkins is an **Author** submitting to *BMJ Open*.
* Dr. Sarah Jenkins is an **Associate Editor** on *Heart*.
* Dr. Sarah Jenkins is an invited **Reviewer** on *The Lancet*.

Pitch It models this by decoupling identity from authority: `User` holds identity (email, name, ORCID), while `JournalMembership` defines roles per journal.

| # | Pitch It Role | Source of Truth | Authentication Mechanism | Permissions & Double-Blind Visibility |
|:---:|:---|:---|:---|:---|
| 1 | **Author** | Peer review platform submission record | Launch token or verified ORCID sign-in | • Record/upload 3-minute pitch for own paper<br>• Access Author Studio and Author Feedback<br>• Zero access to reviewer identities or editor queues |
| 2 | **Handling Editor** | Kriyadocs `users` index (`handlingeditor` / `associateeditor`) | Platform launch token or SSO session | • Full access to Editor Triage Dashboard<br>• Execute decisions (`Accept for Review`, `Request Re-pitch`, `Desk Reject`)<br>• Invite reviewers<br>• **Double-blind restriction**: Anonymized stream ONLY |
| 3 | **Editor-in-Chief (EIC)** | Journal config (`projectList.xml` $\rightarrow$ `<eic-email>`) | Elevated launch token or email match | • All Handling Editor privileges<br>• **Master Unblinding Rights**: Can toggle original video for integrity checks (audit-logged) |
| 4 | **Reviewer (Existing)** | Journal reviewer database in Kriyadocs | 14-day Opaque Magic Link (no password) | • Access Reviewer Page for assigned manuscript<br>• 2-stage gate: pitch & abstract visible before accept; PDF unlocked upon accept<br>• Rubric scoring (4 criteria) + 90s feedback |
| 5 | **Reviewer (New / Guest)** | Added by editor by email; provisional user in Pitch It | 14-day Opaque Magic Link (no password) | • Same as existing reviewer<br>• Optional post-review claim via ORCID or password |
| 6 | **Publisher Admin** | Kriyadocs `admin` / `manager` role | Platform admin login / launch token | • Full access to Pitch It Settings tab<br>• Configure review models, limits (180s/90s/60s), and reminder cadences |

## 4. Launch & Authentication Flows

Pitch It supports two integration patterns: **Flow A (Launch-Token SSO — Primary)** and **Flow B (Credential Forwarding via Service Key — Standalone Fallback)**.

### 4.1 Flow A: Launch-Token SSO (Primary In-Context Path)

When an Author or Editor is working inside Kriyadocs and clicks *"Record Pitch"* or *"Watch Pitch"*, Kriyadocs opens Pitch It in a **new tab (`target="_blank"`)** with a signed, single-use launch token.

### 4.2 Flow B: Credential Forwarding via `kriya2.0` (Direct Bookmark Fallback)

If an Editor navigates directly to `pitch-it.kriyadocs.com` via a browser bookmark, they are presented with a sign-in view. Pitch It does **not** store or check Kriyadocs passwords locally; it forwards the request to Kriyadocs via a dedicated service endpoint:

* **Endpoint:** `POST {env.KRIYA_API_URL}/api/pitchitauthenticate`
* **Security Header:** `X-KD-PITCHIT-AUTH-KEY: {env.KRIYA_PITCHIT_AUTH_KEY}`
* **Behavior:** Validates password with bcrypt against Kriyadocs users, returns user entity and journal memberships, without setting or modifying Kriyadocs portal session cookies.

## 5. Reviewer Architecture: Opaque Magic Links & 2-Stage Confidentiality Gate

### 5.1 Why Opaque Random Tokens (Not JWTs)
The previous revision considered a stateless JWT in the URL. That approach had critical security and privacy flaws:
1. **Double-Blind Identity Leakage:** Any standard JWT in a URL contains Base64-encoded JSON. Anyone reading browser history, server access logs, or proxy logs can decode the reviewer's name, email, and manuscript title.
2. **Revocation Impossibility:** If an editor cancels an invitation, a stateless JWT remains valid until expiration.
3. **State Desynchronization:** Storing `canDownloadPdf` in a JWT forces a new token to be minted upon acceptance.

### 5.2 The Opaque Token Solution
1. When an invitation is generated, Pitch It creates a high-entropy 32-byte cryptographically secure random token:
   ```ts
   const rawToken = crypto.randomBytes(32).toString('hex'); // 64 chars
   const tokenHash = crypto.createHash('sha256').update(rawToken).digest('hex');
   ```
2. The raw token is dispatched in the invitation email URL:
   ```
   https://pitch-it.kriyadocs.com/reviewer-feedback?token=<rawToken>
   ```
3. Only the `tokenHash` is persisted in the PostgreSQL `ReviewAssignment` table.
4. When the reviewer opens the link:
   - Pitch It hashes the incoming token (`sha256(rawToken)`) and performs a constant-time lookup.
   - It checks `status !== 'DECLINED' && status !== 'EXPIRED' && deadlineAt > now()`.
   - Permissions and access state are derived entirely from the database row (`status: INVITED` vs `status: ACCEPTED`).

```mermaid
sequenceDiagram
    autonumber
    actor Reviewer as Peer Reviewer
    participant Client as Pitch It Frontend
    participant Server as Pitch It Fastify Server
    participant DB as PostgreSQL

    Reviewer->>Client: Clicks email link (/reviewer-feedback?token=rawToken)
    Client->>Server: GET /api/v1/reviewer/session?token=rawToken
    Server->>Server: Computes sha256(rawToken)
    Server->>DB: SELECT * FROM ReviewAssignment WHERE tokenHash = hash
    DB-->>Server: Returns assignment record (status: INVITED)
    Server-->>Client: Returns { reviewerPseudonym, abstract, streamUrl, canDownloadPdf: false }
    Note over Client: Reviewer watches 3-min pitch & reads abstract.<br/>Full manuscript PDF is cryptographically locked.

    Reviewer->>Client: Clicks "Accept Invitation"
    Client->>Server: POST /api/v1/reviewer/accept (token: rawToken)
    Server->>DB: UPDATE ReviewAssignment SET status = 'ACCEPTED', acceptedAt = now()
    Server->>KD: Emits Webhook: reviewer.accepted
    Server-->>Client: 200 OK { canDownloadPdf: true, pdfUrl: "/api/v1/manuscripts/.../pdf" }
    Note over Client: PDF download unlocks; 4 rubric sliders and<br/>90s feedback recorder are revealed.
```

## 6. Author KYC & Identity Verification Engine

Pitch It enforces a **3-Tier Scientific KYC Trust Pipeline** (`FR-2.2`, `FR-3.4`) to confirm that a legitimate researcher stands behind every submission.

```
                           [ Author Submits Pitch ]
                                       │
                ┌──────────────────────┴──────────────────────┐
                ▼                                             ▼
       [ ORCID Public Record ]                       [ Email & Recording ]
                │                                             │
                ├─ Queried via pub.orcid.org                  ├─ Trusted domain whitelist or academic TLD?
                ├─ Trusted-source works (Crossref/DataCite)   └─ Live webcam recording completed?
                │  count ≥ 2? Account age > 180 days?         │
                │                                             │
                └──────────────────────┬──────────────────────┘
                                       │
                      ┌────────────────┴────────────────┐
                      ▼                                 ▼
            [ GREEN TRUST BADGE ]             [ AMBER WARNING BADGE ]
         "Live Recording Confirmed"          "Academic ID Only (No Live)"
         - Live webcam recording +           - Pre-recorded video upload OR
         - Verified institutional email OR   - Slides + written script OR
           established ORCID (≥ 2 papers)    - New/unverified ORCID with
                                               personal email (@gmail.com)
```

### 6.1 Direct Public ORCID Ingestion
Kriyadocs stores only the author's `orcidId`. To verify trusted works, Pitch It queries ORCID's public API directly:
* **API Call:** `GET https://pub.orcid.org/v3.0/{orcidId}/works` (Header: `Accept: application/json`)
* **Filtering Criteria:** Works are counted toward the threshold **only if** their `source.source-client-id` corresponds to a verified publishing entity (Crossref, DataCite, PubMed Central, or a registered publisher client). Manually self-reported works are ignored to prevent paper mill spoofing.

### 6.2 Institutional Domain Verification
Blanket `.org`, `.net`, or generic top-level domains are treated as personal. Institutional domains are validated against:
1. **Academic Top-Level & Second-Level Domains:** `.edu`, `.ac.uk`, `.edu.*`, `.ac.*`, `.res.in`, `.gov`, `.mil`.
2. **Maintained Academic Domain Whitelist:** Known universities and research institutes (e.g. `ox.ac.uk`, `cam.ac.uk`, `nih.gov`, `nhs.uk`, `maxplanck.de`).
3. **Personal Email Policy:** Authors with personal addresses (`@gmail.com`) earn the **Green Badge** as long as they complete a live webcam recording and possess an established ORCID record ($\ge 2$ trusted works, account age $> 180$ days).

## 7. Editor Privileges & Master Unblinding Architecture

In Double-Blind Peer Review, strict server-side authorization guards prevent identity leakage:

* **Handling Editor:** When calling `GET /api/v1/manuscripts/:id/stream`, Fastify inspects the session role. For double-blind manuscripts, the server **omits the master stream URL entirely** and returns only the Cadmore token for the neutral avatar HLS playlist.
* **Editor-in-Chief (EIC):** The EIC holds master integrity authority.
  - EIC status is verified: `user.email.toLowerCase() === journal.eicEmail.toLowerCase()`.
  - When the EIC toggles *"Show Original Video"*:
    1. Fastify writes an immutable record to PostgreSQL `AuditLog` (`action: "eic_unblind_accessed"`).
    2. Issues a short-lived (5-minute expiry) signed URL for the master un-anonymized video stream.

## 9. Frontend State Hydration & UI Mapping

To prevent stack drift and ensure secure session management:
* **Display Mode:** Pitch It opens in a **new tab (`target="_blank"`)**, ensuring full hardware access to cameras/microphones and avoiding iframe security boundaries.
* **Cookie Mode:** Pitch It issues an HTTP-only, secure, `SameSite=Lax` cookie (`pitchit_session`).
* **State Management:** Session data is managed via **TanStack Query** (`useAuthSession` hook calling `GET /api/v1/auth/me`).

### 9.1 TanStack Query Auth Hook (`client/src/hooks/useAuthSession.ts`)
```ts
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';
import { apiClient } from '../lib/apiClient';

export interface AuthUser {
  id: string;
  name: string;
  email: string;
  activeRole: 'AUTHOR' | 'HANDLING_EDITOR' | 'EDITOR_IN_CHIEF' | 'REVIEWER_EXISTING' | 'REVIEWER_GUEST' | 'PUBLISHER_ADMIN';
  orcidId?: string;
  isOrcidVerified: boolean;
  institution?: string;
  activeJournalCode: string;
}

export function useAuthSession() {
  const queryClient = useQueryClient();

  const sessionQuery = useQuery<AuthUser | null>({
    queryKey: ['auth', 'session'],
    queryFn: async () => {
      try {
        const res = await apiClient.get('/api/v1/auth/me');
        return res.data.user;
      } catch {
        return null;
      }
    },
    staleTime: 5 * 60 * 1000,
    retry: false
  });

  const exchangeTokenMutation = useMutation({
    mutationFn: async (launchToken: string) => {
      const res = await apiClient.post('/api/v1/auth/exchange-token', { token: launchToken });
      return res.data.user;
    },
    onSuccess: (user) => {
      queryClient.setQueryData(['auth', 'session'], user);
      // Clean launch token from URL address bar without reloading page
      window.history.replaceState({}, document.title, window.location.pathname);
    }
  });

  return {
    user: sessionQuery.data ?? null,
    isLoading: sessionQuery.isLoading,
    isAuthenticated: !!sessionQuery.data,
    exchangeToken: exchangeTokenMutation.mutateAsync,
    logout: async () => {
      await apiClient.post('/api/v1/auth/logout');
      queryClient.setQueryData(['auth', 'session'], null);
    }
  };
}
```

## 10. Security, Privacy & Network Configuration

1. **Replay & Forgery Prevention:**
   - Launch tokens are signed using **RS256**. Pitch It verifies them against Kriyadocs' public key (`KRIYA_PUBLIC_KEY`).
   - Every launch token carries a unique `jti`. Pitch It verifies that the `jti` has not been redeemed, recording it in `UsedLaunchToken` table.
2. **Opaque Tokens Protect Double-Blind Review:**
   - Reviewer magic links carry high-entropy 32-byte opaque strings. No metadata, reviewer identities, or manuscript titles exist in URLs, browser history, or server access logs.
3. **Network & Proxy Configuration:**
   - Fastify is configured with `trustProxy: true` to inspect `X-Forwarded-For` headers behind AWS ALB/CloudFront, ensuring rate limits (`@fastify/rate-limit` capped at 10 requests per minute per IP) operate on real client IPs.
4. **Cadmore Media Secrets Management:**
   - In accordance with `FR-1.9`, the Publisher Admin Settings Tab displays only **connection health status**.
   - Cadmore credentials (`CADMORE_API_KEY`, `CADMORE_SECRET`) are server-side environment variables loaded from AWS Secrets Manager, never exposed in client bundles or admin UI fields.

### 11.1 Proposed Kriyadocs Engineering RFC (Ticket Specification)

To integrate Pitch It cleanly without risking session collisions, the following formal ticket specification should be submitted to the Kriyadocs Core Team:

* **Title:** `[Pitch It] Add RS256 Launch-Token SSO, /api/pitchitauthenticate, and Reviewer Search API`
* **Precedent:** Follows PRs [#652](https://github.com/kriyadocs-engineering/kriya2.0/pull/652) and [#711](https://github.com/kriyadocs-engineering/kriya2.0/pull/711) in `kriya2.0`.
* **Required Additions:**
  1. **RS256 Launch Action (Flow A):**  
     When clicking *"Watch Pitch"* or *"Record Pitch"* in the Kriyadocs dashboard, open Pitch It in a new tab (`https://pitch-it.kriyadocs.com/?token=<JWT>`), signed with Kriyadocs' private key, carrying user identity, active journal code, journal EIC email, and a unique `jti` (5-minute expiry).
  2. **Direct Auth Endpoint (Flow B):**  
     Provide `POST /api/pitchitauthenticate`, callable with header `X-KD-PITCHIT-AUTH-KEY`. Validates credentials via bcrypt and returns user metadata and journal memberships without setting portal cookies.
  3. **Reviewer Search Endpoint:**  
     Provide `POST /api/pitchit/reviewers/search`, callable with header `X-KD-PITCHIT-AUTH-KEY`. Proxies `elasticnodeproxy` query template `getuserswithjournals` to search reviewers by journal, keywords, and turnaround stats.
